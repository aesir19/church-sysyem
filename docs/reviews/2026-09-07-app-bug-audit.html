High · F1Staging reproduced

A later finance migration removed Events Team permission to add an event expense

Trigger: an Events Team member adds an expense to an event they manage.

Actual result: PostgreSQL rejects the insert with 42501, “new row violates row-level security policy for table expenses.”

Cause: migration 0035 widened expenses_insert_own_church with is_own_event_expense(event_id). Migration 0039 later drops and recreates that policy with only the Finance branch, unintentionally erasing the Events Team branch.

Proposed solution: add a new forward-only migration that combines the Finance and owned-event authorization branches, while applying the correction-integrity constraints to both. Do not edit migration history.

Regression guard: keep the existing allowed insert test; add denials for an event-less expense, an event in another church, and a crafted reversal/correction payload.

Done when: Events Team can add a normal entry only to an event it owns; Finance retains its current permissions; all correction rules remain fail-closed.

High · F2Control flow confirmed

Splitting or deleting an event series can leave partially applied data

Trigger: a later request in a series split/delete fails because of a network interruption, RLS denial, or constraint.

Actual risk: splitSeries first shortens the old series, then creates the new one, then moves exceptions. deleteSeries detaches past rows, deletes future exceptions, then deletes the series. Each step commits independently.

Impact: the operation can report failure after already changing part of the schedule.

Proposed solution: move each operation into a narrow PostgreSQL RPC so the complete mutation runs in one transaction. The function must authorize church and event-management scope internally.

Regression guard: force a failure in the final stage and prove the original series and exceptions remain unchanged.

Done when: each series operation either completes in full or leaves the database exactly as it was before the request.
src/lib/data/eventSeries.js:286–315 → three-step split
src/lib/data/eventSeries.js:321–339 → three-step delete
Medium · F3Browser reproduced

A slow Events request can overwrite the currently selected tab

Trigger: open Events, then switch from Upcoming to Drafts while the first request is still in flight.

Actual result: Drafts renders correctly, then the older Upcoming response arrives and replaces the shared event list while the Drafts tab remains selected.

Cause: load() reads reactive scope, awaits, and writes shared state without a request generation check or cancellation.

Proposed solution: capture tab and church at request start, assign a monotonic request token, and discard success, error, and loading-state updates from superseded requests. An AbortController may reduce wasted work but should not be the only correctness guard.

Regression guard: retain the delayed-response browser scenario and assert the Drafts result remains after both requests settle.

Done when: displayed rows always match the visibly selected tab and church, regardless of response order.
src/views/EventsView.vue:41–60 → shared state with overlapping watcher loads
Targeted Playwright repro: Draft row appeared, then disappeared after delayed Upcoming response
Medium · F4Unit reproduced

A transient active-church lookup failure is cached as a successful load

Trigger: get_my_church returns a temporary error during initial application load.

Actual result: the composable stores a null church, sets loaded = true, and subsequent ensureLoaded() calls do not retry. If the promise rejects outright, pending also lacks guaranteed cleanup.

Impact: church-scoped screens can remain empty or unusable until the session is reset.

Proposed solution: treat RPC errors as an unsuccessful load, set loaded only after required context is valid, and clear pending in finally. Expose a generic retry state without revealing backend details.

Regression guard: first lookup fails, second succeeds, and the second call must reissue the RPC and populate the church.

Done when: a temporary startup failure can recover in the same signed-in session without stale rejected promises.
src/composables/useActiveChurch.js:44–69 → RPC errors ignored and loaded state finalized
Targeted unit repro: expected church-1 after recovery; received null; RPC called once
Medium · F5Control flow confirmed

Event detail can disguise a read failure as a virtual event or “not found”

Trigger: the real-event lookup fails, but the series lookup succeeds—or no matching series exists.

Actual result: the view checks only real.event, not real.ok. It can continue into virtual occurrence matching or show “That event could not be found.”

Impact: an outage or permission problem is presented as absence. A computed occurrence can also be shown when a saved exception or cancellation could not be read.

Proposed solution: stop immediately when the real-event result is not ok; show the generic load error and a retry action. Only attempt virtual fallback after a successful lookup returns no row. Apply the same result handling to series and link reads.

Regression guard: return an events endpoint error with a valid recurring series and assert that neither the virtual detail nor “not found” is displayed.

Done when: “not found” means a successful search found nothing; operational failures are visibly recoverable errors.
src/views/EventDetailView.vue:144–169 → error result falls through into virtual lookup and not-found state
Systemic risks and gaps

Important follow-up work, not additional confirmed defects

Pattern risk

The Events race pattern appears in other shared-state loaders

Members, Calendar, Attendance, finance views, Funds, and Groups contain similar “watch → await → write shared refs” loaders. The Events failure proves the pattern is unsafe, but this audit did not reproduce a wrong-state outcome in every screen.

Later review: introduce one small request-scope helper, then test rapid filter/church changes in each screen before rolling it out. Church-switch races deserve priority because they may affect PII visibility, even though no cross-church disclosure was observed here.

Coverage gap

The newest event workflows sit outside the existing browser suite

The 44 passing browser tests cover Attendance, Collections, Expenses, Funds, Groups, Login, Members, Password Reset, and RBAC. There are no equivalent end-to-end files for Overview, Calendar, Events, Event Detail/Composer, Settings administration, or public volunteering.

Later review: add a compact event/calendar suite around loading, errors, response ordering, and role boundaries. To preserve the project’s $0/month constraint, keep database integration checks as a manual pre-promotion gate unless CI usage has been explicitly budgeted.

Proposed fix sequence

Make each fix independently reviewable

Restore invariants

First repair the event-expense policy with a forward migration, then make series mutations transactional. These are the two defects that affect authorization and durable data.

Make async scope explicit

Add stale-response protection to Events, fix active-church retry semantics, and audit the same loader pattern in church-sensitive screens.

Tell the truth on failure

Correct Event Detail error branching, then add the missing event/calendar browser coverage as the acceptance gate for the full pass.

Implementation discipline: each later patch should include its regression test, owner-visible UI evidence where the screen changes, and a security check against the exact role/church boundary it touches.
Scope and limits

A deep technical pass, not a claim of exhaustive correctness

  • Reviewed baseline: branch codex/promote-overview-production at c52ec5c, including the pending Overview promotion in PR #102.
  • Staging baseline: database migrations through 0041 were applied; local 0042 belongs to the pending Overview promotion and was not applied during this audit.
  • Methods: repository inspection, existing unit/build/browser/database suites, and two temporary deterministic repro tests.
  • Security outcome: no broad authorization bypass was confirmed. One legitimate Events Team action is denied. Passing checks are evidence for covered contracts, not proof that every path is secure.
  • Not covered: every role on every page, real mobile devices, long-running offline/session-expiry behavior, load/performance limits, third-party service failures, full accessibility conformance, and production data correctness.
  • Changes made: this report only. No application source, database migration, production deployment, or persistent test harness was changed.
Finding classification
